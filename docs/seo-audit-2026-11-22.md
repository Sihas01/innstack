## Findings and remediation

### 1. DNS, redirects and deployment

- Apex `innstack.online` resolved through both the system resolver and Google Public DNS. A records were `104.21.76.110` and `172.67.193.95`; AAAA records were `2606:4700:3034::6815:4c6e` and `2606:4700:3032::ac43:c15f`. These are observations, not recommended records to enter manually.
- Nameservers: `ajay.ns.cloudflare.com` and `journey.ns.cloudflare.com`.
- Google Public DNS returned no DS answer and `AD: false`; no DNSSEC-related SERVFAIL was reproduced. This does not establish historical DNS reliability.
- `https://innstack.online/` returned 200. HTTP returned 301 to the HTTPS apex. A deep-path HTTP test preserved the path and query string.
- Both A and AAAA queries for `www.innstack.online` returned NXDOMAIN; HTTP clients consequently failed before a redirect could occur. The site uses apex canonicals. This is a concrete missing hostname, **not proof of the reported apex DNS failure**.
- Slashless guide URLs returned 307 to their trailing-slash version. Existing old PMS and RevPAR URLs returned 301 to their intended canonical destinations. These are functional redirects; no speculative redirect changes were made.
- `wrangler.jsonc` deploys a Worker with static assets, `run_worker_first: true`, automatic slash handling and a 404 fallback. It declares no DNS records or custom-domain routes. Bindings therefore require dashboard inspection.
- Corrected README deployment instructions that incorrectly referred to Pages. Production `NEXT_PUBLIC_SITE_URL` must be the HTTPS apex at build time; `PUBLIC_SITE_URL` is a separate Worker runtime setting.

**Manual follow-up:** obtain the exact Semrush failed URL, time and resolver details. In Cloudflare/registrar accounts verify delegation, DNS records, domain binding, certificate status, deployment logs and any recent DNS changes. Inspect Security Events for crawler challenges separately from DNS failures. If `www` is intended to work, provision its DNS/domain and valid TLS certificate using the hosting provider's documented setup, then permanently redirect to apex while preserving path/query. A code redirect cannot fix NXDOMAIN. Do not whitelist crawlers or change DNS without evidence.

### 2. RevPAR structured data

The live page and repository had `WebPage`, nested `SoftwareApplication`/`Offer`, `BreadcrumbList` and `Organization` data. JSON parsed successfully. **No invalid Schema.org property was reproduced in that version.** In particular, `headline` is inherited from `CreativeWork`, `applicationCategory` accepts text, and `Offer.price` accepts text or a number. A string `"0"` is not inherently invalid.

Made the app description more specific and supportable:

- `WebApplication`, a subtype of `SoftwareApplication`, describes the browser calculator.
- Replaced the overly broad operating-system claim `Any` with `browserRequirements`: JavaScript and a modern browser.
- Added the actual application URL and boolean `isAccessibleForFree`.
- Retained the truthful zero-price offer using numeric `0` and `USD`.
- Preserved page, publisher and breadcrumb markup. Added no reviews, ratings, downloads or unverified platform claims.

Checked the revised RevPAR graph against the current Schema.org vocabulary: ten typed nodes, no unknown properties or property-domain mismatches. Values were reviewed against the applicable definitions. This is not a claim that Google's Rich Results Test has passed. Software rich-result eligibility has requirements beyond Schema.org validity, including genuine review/rating evidence; fabricated ratings are not an acceptable fix.

References: [WebApplication](https://schema.org/WebApplication), [SoftwareApplication](https://schema.org/SoftwareApplication), [browserRequirements](https://schema.org/browserRequirements), [isAccessibleForFree](https://schema.org/isAccessibleForFree), [Offer](https://schema.org/Offer).

**Manual follow-up:** obtain Semrush's exact field-level error and captured markup; validate the deployed page in Schema.org Validator and Google's Rich Results Test. A stale crawl or rich-result eligibility rule may explain the discrepancy, but neither has been established.

### 8. HTTPS, HSTS and indexing

- HTTPS worked for the apex and every sitemap URL with normal certificate validation.
- HSTS was absent from the observed apex responses and from repository headers. Left it disabled: subdomain HTTPS coverage is not established and `www` does not resolve. Do not enable `includeSubDomains` or preload on the basis of this audit. An owner can assess a short, apex-only rollout after verifying all affected services.
- Live `robots.txt` returned 200, allows public crawling, disallows `/admin/` and `/api/admin/`, and points to the correct HTTPS sitemap.
- Sitemap returned 200 with 29 canonical public URLs; it excludes Studio, unpublished vendor profiles and the legacy RevPAR alias.
- All 29 public URLs returned 200, had matching absolute HTTPS trailing-slash canonicals and Open Graph URLs, descriptions, social titles and Twitter card metadata. No public sitemap page had a meta or HTTP noindex directive.
- Open Graph images are available for guides with configured featured images. Not every page has a social image; this is not an indexing error.
- A deliberately nonexistent URL returned HTTP 404 and meta noindex.
- The exported Studio page already has noindex metadata, but the Worker's unauthenticated login page bypasses it. Added `X-Robots-Tag: noindex, nofollow, noarchive` to that login response. Authentication and publishing behavior are unchanged. Robots disallow is not an authentication mechanism and may prevent a crawler from seeing noindex; account access remains protected server-side.
- Preview/workers.dev origins and zone-level headers require account access to verify.
